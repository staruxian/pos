# CLAUDE.md

POS (касса) для магазина одежды «Shaxzoda Premium». React 19 + Vite SPA, Bun-сервер,
Turso (libSQL) как база. Деплой на Vercel.

## Команды

```bash
bun run dev          # сервер (:3001) + Vite (:5173) параллельно
bun run dev:server   # только API, bun --watch server/index.ts
bun run dev:client   # только фронтенд
bun run build        # vite build -> dist/
bun run start        # прод-сервер
```

Тестов и линтера в проекте нет. Проверка типов — `bunx tsc --noEmit`.

## Архитектура

- `server/auth.ts` — вход по общему паролю магазина и подписанная сессия в cookie.
- `server/security.ts` — разбор `__path`, лимит размера тела, счётчик запросов, CSPRNG.
- `server/index.ts` — весь API. Один экспорт `handle(req)`: плоская цепочка
  `if (method === ... && pathname === ...)` без роутера. Ответы — через хелперы
  `json()` / `error()`. `fetchApi()` оборачивает `handle` в CORS и `try/catch`.
  Запускает `Bun.serve` только под `import.meta.main`.
- `api/index.ts` — тонкая обёртка для Vercel Functions, экспортирует `{ fetch: fetchApi }`.
- `server/db.ts` — клиент libSQL, схема (`CREATE TABLE IF NOT EXISTS` + ручные
  `ALTER TABLE` для добавленных колонок), обёртка `db.query(sql).all/get/run(...args)`
  в стиле `bun:sqlite`, и `withTransaction(tx => ...)`. Все вызовы ждут `dbReady`.
- `src/lib/api.ts` — типы доменных сущностей и объект `api` с методами `fetch`.
  Единая распаковка ответа в `parse<T>()`.
- `src/App.tsx` — layout + вкладки, держит список товаров в состоянии и раздаёт его
  страницам через `useOutletContext`. Роуты объявлены в `src/main.tsx`.
- `src/pages/*.tsx` — пять экранов: Касса, Товары, Клиенты, Баланс, Отчёты.
- `src/components/ui/*` — shadcn/ui (new-york, base color neutral), алиас `@/*` → `src/*`.
- `src/components/page-header.tsx` и `stat-card.tsx` — общие блоки всех экранов:
  шапка страницы и плитка показателя. Новый экран собирайте из них, чтобы страницы
  не разъезжались по типографике и отступам.

Каталога товаров на Кассе нет: экран — это поле ввода и корзина. Сканер вводит цифры
и товар уходит в корзину сразу; буквы в том же поле означают поиск по названию, и под
ним появляется короткий список подсказок.

Таблицы: `products`, `sales`, `sale_items` (с денормализованными `product_name`/`sku`
и `cost_price`), `clients`, `client_ledger` (`kind` = `debt` | `payment`), `expenses`.
Баланс клиента нигде не хранится — он всегда считается суммой по `client_ledger`.

## Вход и сессии

Вход по паролю **необязателен** и включается наличием `POS_PASSWORD` и
`SESSION_SECRET`. Если их нет, `authEnabled()` возвращает false, проверка
пропускается и API открыт всем — сейчас в проде именно так. Заданная лишь одна
из двух переменных считается ошибкой настройки: API отвечает 503, потому что
непонятно, хотели включить вход или нет. Что происходит на самом деле, видно
по `GET /api/health` — он отдаёт `auth: "enabled" | "disabled"`.

Аутентификации по пользователям нет — есть один пароль магазина (`POS_PASSWORD`).
`POST /api/login` проверяет его за постоянное время и выдаёт cookie `pos_session`:
HttpOnly, SameSite=Strict, срок 12 часов, подпись HMAC-SHA256 на `SESSION_SECRET`.
Токен самодостаточен, в базе ничего не хранится; смена `SESSION_SECRET` завершает
все сессии.

Когда вход включён, публичны только `/api/health`, `/api/login`, `/api/logout` и
`/api/session` — всё остальное отвечает 401 без сессии. Список в `publicPaths`;
**новый маршрут закрыт по умолчанию**, специально ничего делать не нужно.

`process.env` читается на каждом запросе, а не при импорте: Vercel фиксирует
переменные в момент создания деплоя, а падение на верхнем уровне модуля убивает
функцию целиком — тогда даже `/api/health` отвечает безликим 500.

На клиенте `parse()` в `src/lib/api.ts` на 401 бросает `UnauthorizedError` и шлёт
событие `pos:unauthorized`; `App` ловит его и показывает `LoginPage`.

CORS намеренно отсутствует: фронтенд и API живут на одном origin (в разработке —
через прокси Vite), поэтому чужим сайтам обращаться сюда незачем.

## Три цены товара

У товара две цены: `products.cost_price` — закупочная, `products.price` — продажная.
Фактическая цена продажи у товара не хранится, она принадлежит сделке: кассир может
менять её в диалоге на Кассе, и она уходит в `sale_items.unit_price`. Поэтому
`POST /api/sales` принимает у позиции необязательный `unit_price` (без него берётся
`products.price`) и схлопывает позиции по паре «товар + цена», а остаток проверяет
по суммарному количеству товара во всей продаже.

`sale_items.cost_price` — снимок закупочной цены на момент продажи: без него
переоценка товара задним числом меняла бы прибыль за прошлые периоды. Прибыль в
`GET /api/reports` считается только по этому снимку.

Уже проведённую продажу можно поправить из «Последних продаж» в Отчётах:
`PATCH /api/sales/:id` меняет **только** `unit_price` позиций и пересобирает
`sales.total` из позиций (не правит его на разницу), а `DELETE /api/sales/:id`
отменяет продажу и возвращает товар на склад. Состав и количество не редактируются —
иначе пришлось бы пересчитывать остатки задним числом. Позиции удаляются явно:
`ON DELETE CASCADE` работает только при включённых внешних ключах.

## Баланс, расходы и изъятия

Ничего из этого не хранится: `GET /api/balance` каждый раз считает всё заново — как и
баланс клиента по `client_ledger`. Поэтому отмена продажи или удаление записи сразу
возвращают цифры назад, без отдельной бухгалтерии.

Списания бывают двух видов, и это главное различие в разделе (`expenses.kind`):

- `expense` — трата магазина (аренда, пакеты). Уменьшает **и баланс, и прибыль**.
- `withdrawal` — деньги вынули из кассы. Уменьшает **только баланс**: это уже
  заработанные деньги, а не затрата, поэтому прибыль не трогает.

Отсюда формулы: `balance = продажи − расходы − изъятия`,
`margin = SUM(qty × (unit_price − cost_price))` по `sale_items` (только проданное,
по ценам и закупке той продажи), `profit = margin − расходы`.

`margin` считается по проданному, а не по остаткам: прогноз «если продать всё по
прайсу» ничего не говорит о том, заработал магазин или нет. Плитка «Чистая прибыль»
на Товарах берёт `profit` отсюда же — на всех экранах это одно и то же число.

Каждый вид операций идёт своим списком (`sales`, `expenses`, `withdrawals`, по 50
последних) — в одной ленте расходы терялись среди продаж. У расхода комментарий
**обязателен** (`POST /api/expenses` отвергает пустой): трату без пояснения потом
невозможно разобрать. У изъятия он необязателен. Продажа из списка не удаляется —
она правится и отменяется в Отчётах, чтобы не было двух разных путей отмены.

Долги клиентов в баланс намеренно не входят: продажа в долг уже учтена как продажа,
и приём оплаты по `client_ledger` добавил бы ту же сумму второй раз.

## Деньги — целые тийины, не дробные сумы

`price`, `cost_price`, `total`, `unit_price` и `amount` хранятся и передаются целым
числом тийинов (1/100 сума). Конвертация только на границе с формами: `toMinor()` при
отправке, `fromMinor()` для заполнения поля, `money()` для вывода (все в
`src/lib/utils.ts`). Сервер требует целое число и отвергает дробное.

Старые базы переводит одноразовая миграция `money-minor-units-v1` в `server/db.ts`:
она умножает суммы на 100 и ставит отметку в таблице `meta` в той же транзакции.
Повторно не сработает, но **необратима** — перед первым деплоем сделайте дамп базы.

## На Vercel все `/api/*` переписываются в одну функцию

`vercel.json` переписывает `/api/:path*` → `/api?__path=/api/:path*`, поэтому
`handle()` берёт путь из `url.searchParams.get("__path") ?? url.pathname`.
Новые роуты пишите от полного пути `/api/...`, иначе в проде они не найдутся.
Второй rewrite отдаёт `index.html` всему, что не `/api`, — для SPA-роутинга.

`__path` подконтролен клиенту, поэтому `resolvePath()` доверяет ему только когда
запрос пришёл на `/api` и значение — корректный путь `/api/...`. Иначе фильтр по
пути на уровне платформы (Deployment Protection, WAF) обходился бы через `?__path=`.

## Печать этикеток

Печать идёт не из браузера, а через локальный мост к Xprinter (`src/lib/printer.ts`,
`VITE_PRINT_URL`, по умолчанию `http://localhost:5000/print`). Мост принимает
`{ data, text }` и сам формирует этикетку 60 × 30 мм. Сервер отдельно рендерит
SVG-штрихкод Code 128 через `bwip-js` на `GET /api/products/:id/barcode` — это только
для предпросмотра в диалоге, печать через него не идёт.

Мост подставляет подпись в шаблон команд принтера, поэтому `printLabel()` вырезает
из названия управляющие символы, кавычки и слеши и обрезает строку до 64 символов.
Сам мост живёт вне этого репозитория: его CORS должен быть ограничен origin кассы,
иначе печатать сможет любой открытый в браузере сайт.

## Соглашения

- Язык интерфейса и текстов ошибок — русский. Все сообщения пользователю пишите по-русски;
  комментарии в коде тоже русские, и их немного — только там, где неочевидно «почему».
- Валидация целиком на сервере, ответ — `error("Сообщение", status)`. Клиент показывает
  `err.message` как есть.
- Подтверждение необратимых действий — только через `ConfirmDialog`
  (`src/components/confirm-dialog.tsx`), никаких `window.confirm()` и `alert()`.
  Браузер разрешает подавить системные диалоги («не показывать больше»), после чего
  `confirm()` молча возвращает false: кнопка выглядит нажатой, но не делает ничего и
  не шлёт запрос. Ошибку сервера показывайте в самом диалоге, оставляя его открытым.
- Ошибки БД не глушим: `catch` ловит только `isUniqueViolation(e)`, остальное летит
  наверх и логируется как 500. Иначе сбой соединения выглядел бы как дубликат штрихкода.
- Штрихкод (`sku`) — только цифры; при создании товара без него генерируется 12-значный
  в `newBarcode()`.
- Суммы форматируются `money()` из `src/lib/utils.ts` (локаль `ru-RU`).
- Даты хранятся строкой `datetime('now', 'localtime')`, сравнения по диапазону — строковые.
- В шапке `App` размытие вынесено в отдельный слой под содержимым. `backdrop-filter`
  создаёт containing block для потомков с `position: fixed`, и нижняя панель вкладок
  прилипала к шапке вместо низа окна — на телефоне она закрывала название магазина.

## Окружение

`.env` (не в git) должен задавать `TURSO_DATABASE_URL` и `TURSO_AUTH_TOKEN` — без
них `server/db.ts` падает на старте. `POS_PASSWORD` и `SESSION_SECRET`
необязательны и включают вход по паролю; задавать их нужно парой.
Образец — `.env.example`.

На Vercel переменные, ограниченные только Production, не попадают в Preview-деплой.
Если приложение их не видит, сверьтесь с областью действия: `TURSO_*` заданы как
Production **и** Preview, и именно поэтому доходят.

Заголовки безопасности (CSP, nosniff, HSTS, frame-ancestors) заданы в `vercel.json`
и действуют только в проде. `connect-src` в CSP перечисляет адрес моста печати —
при смене `VITE_PRINT_URL` обновите и его.
